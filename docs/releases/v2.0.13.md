The application version for this milestone is **2.0.13** in:

Report schema remains **v2**. Application version 2.0.13 does not change report-schema semantics. Valid schema-v1 and schema-v2 import behavior remains as documented in `docs/report-schema.md`.

## Source changes in 2.0.13

### Reproducible release preflight

- Added `npm run release:readiness`.
- Tagged release packaging now requires reviewed, committed `package-lock.json` and `src-tauri/Cargo.lock` files.
- The preflight validates basic lockfile structure, rejects obvious merge-conflict markers, checks npm root-version alignment when present, and prints SHA-256 fingerprints for both locks.
- Tagged frontend installation now uses `npm ci` instead of resolving dependencies with `npm install`.
- Cargo manifest/lock alignment is checked with `cargo metadata --locked` before native packaging.

These controls intentionally block a tagged release while the repository does not yet contain reviewed lockfiles. Lockfiles must be generated by npm/Cargo in a registry-capable environment; they must not be hand-authored merely to satisfy the gate.

### Review-only dependency lock candidate generation

- Added manually dispatched `.github/workflows/dependency-lock-candidate.yml`.
- The workflow generates `package-lock.json` with `--package-lock-only --ignore-scripts` and generates `src-tauri/Cargo.lock` with Cargo on a clean Ubuntu runner.
- It validates the generated locks with `npm run release:readiness` and `cargo metadata --locked`.
- It uploads both files as a temporary seven-day review artifact.
- Repository permissions are read-only; the workflow deliberately cannot auto-commit or push dependency changes.

This provides a real registry/toolchain path for producing lockfile candidates without weakening the requirement for human dependency review before those files enter source control.

### Release evidence capture

- Added `npm run release:evidence -- <output.json>`.
- Evidence schema v1 records application version, capture time, allowlisted GitHub runner/ref identity, OS/architecture, Node/npm/rustc/Cargo version availability, build status supplied by CI, and dependency-lock SHA-256 fingerprints.
- Generated `release-evidence/` output is ignored by Git.
- The tagged release workflow uploads per-platform build evidence even after a packaging failure when the evidence writer can run.

The evidence writer does not read analyzed documents, reports, settings, signing secrets, credentials, or arbitrary environment variables.

### Cross-platform release-candidate audit

- Added manually dispatched `.github/workflows/release-candidate.yml`.
- The workflow uses clean GitHub-hosted Ubuntu 22.04, Windows, and macOS runners.
- It requires the dependency-lock preflight, installs with `npm ci`, validates Cargo with `--locked`, runs frontend quality gates, Rust format/Clippy/tests, attempts native Tauri bundles, and uploads temporary bundles plus evidence.
- Ubuntu additionally records the existing release-mode synthetic analyzer benchmark.

A successful workflow does not replace manual package installation, native screen-reader/scaling/reduced-motion review, screenshot capture, signing/notarization, or final checksum verification.

### Security/release policy corrections

- Corrected `SECURITY.md` so the supported line reflects current 2.0.x development rather than the old 0.1.x-only wording.
- Added dependency-advisory triage rules: memory-safety/unsoundness advisories remain release-review blockers until patched or technically assessed, unmaintained notices require upstream/dependency-path review, and advisories must not be suppressed solely to make automation green.
- Expanded the release template with lockfile, evidence, advisory, native-platform, accessibility, signing, and checksum acceptance records.
- Added `docs/release-evidence.md` describing exactly what automated evidence proves and what remains manual.

## Open dependency advisory status

The scheduled Rust audit opened multiple public RustSec tracking issues on 2026-08-24 for transitive dependencies, including an unsound `glib` version advisory (`RUSTSEC-2024-0429`) and several unmaintained GTK3/UNIC ecosystem packages.

This source milestone does **not** claim those advisories are resolved. Before public binary release:

1. generate and review the real `src-tauri/Cargo.lock`;
2. reproduce the audit against that locked graph;
3. identify the exact dependency path for each release-relevant advisory;
4. prefer supported upstream dependency fixes/migrations;
5. retain unresolved release-relevant items as documented release blockers or limitations rather than hiding them.

## Compatibility and privacy boundaries retained

- Report output remains schema v2; valid schema v1 and v2 imports remain supported.
- Settings backup compatibility is unchanged.
- Source document text remains excluded from canonical exported reports.
- Full private source paths remain outside the report contract.
- Recent-file metadata remains opt-in and path-free.
- No analytics SDK, account requirement, cloud text-processing API, or background update polling was added.
- Release evidence contains build metadata only and does not inspect user documents or local TextLens data.

## External release gates not claimed as complete

The following remain open and must not be represented as completed without actual evidence:

- generate/review/commit npm `package-lock.json` from npm output;
- generate/review/commit `src-tauri/Cargo.lock` from Cargo output;
- run `npm run release:readiness` against those real committed locks;
- run the complete clean frontend/Rust suite from the reviewed dependency graph;
- run the manual Release Candidate Audit successfully on Ubuntu, Windows, and macOS;
- review current RustSec tracking issues against the locked dependency graph and available upstream fixes;
- install and manually exercise every produced platform package;
- complete native screen-reader, scaling, keyboard, and reduced-motion acceptance;
- capture real screenshots from verified packages;
- configure Windows signing and Apple Developer ID/notarization where credentials are available;
- apply repository-admin branch protection/rules;
- generate and verify `SHA256SUMS.txt` for the final artifact set;
- re-run final release-candidate verification before publishing a stable tag/release.

Do not publish a stable `v2.0.13` binary release merely because the source version is prepared or because a draft release workflow exists. Complete and retain the applicable evidence first.
